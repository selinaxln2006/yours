> 姊妹文档：`paa-design-v2.md`（大脑层内部设计，四支柱 C1–C4）

---

## 〇、这份文档为什么存在

2026-08-17 下午，俪宁提出了一个尖锐且正确的质问：

> "我要一个 Codex 级 agent，但你给我搭了一个前端 agent，然后和我说该收手了？"

这是本文档的触发点。先把回答钉死，避免再次误读：

- **生活工作台 PWA 从来不是目标形态，是临时宿主。** 它的使命是验证产品体验（计划卡 UX、Skills 接口形状、多意图识别），不是当 agent 的最终运行载体。
- **"该收手"指的是：停止往临时宿主（index.html）里打功能补丁。** 不是停止推进 Codex 级 agent——那是 PAA 的主线，几乎还没真正开始。
- 前端 agent 永远够不到 Codex 级，**不是补丁数量问题，是浏览器安全沙箱的物理边界**：跑在浏览器里的 JS 天生碰不到自己硬盘上的源码。补丁补不出 FS/shell 权限。

所以本文档回答三个问题：

| # | 问题 | 章节 |
|---|------|------|
| 1 | 我们现在在哪（现状定位） | 一 |
| 2 | 要去哪（Codex 级 agent 的判定标准） | 二 |
| 3 | 怎么去（差距分析 + 宿主外移路线） | 三、四 |

## 一、现状定位：PWA 完成了什么

### 已验证（作为产品验证载体，使命已达成）

| 已验证项 | 内容 | 证据 |
|---------|------|------|
| 计划卡 UX | 写操作走"计划 → 确认 → 执行 → 结果清单"，✅/❌ 展开 | v0.6/v0.6.1 联测 |
| Skills 接口形状 | 13 个内置工具 + `Skills.register()` 挂载点 | Skills 注册表（v0.6） |
| 多意图 hybrid 识别 | 正则规则 + LLM 二次识别双通道 | 识别引擎 |
| 重复日程展开 | rrule weekly/biweekly/monthly + count 换算 | v0.5.x 联测修复 |
| 目标拆解 | 4 类目标自动生成里程碑 + 实时进度 | v0.5.1 |
| 规划链路截断兜底 | 动态兜底总结替代硬编码文案 | Phase 0.2 联测第五轮 |

### 边界（作为 agent 运行载体，硬伤）

| 维度 | PWA 内 | 影响 |
|------|--------|------|
| 存储 | localStorage（按 origin 隔离） | 本地/外部浏览器天然不同步 |
| 权限 | DOM + fetch | 碰不到文件系统、shell |
| 自修改 | 无（源码在文件系统，JS 够不到） | "agent 自己修工作台"在架构上不成立 |
| 计算 | 单线程 + 上下文受限 | 重任务（规划 1500 token 截断）是常态 |

**结论：PWA = 产品验证载体 ✓，agent 运行载体 ✗。** 该收手的是前者，该开始的是后者。

## 二、目标形态：Codex 级 agent 的判定标准

定义一套**可打勾的判定清单**（G1–G7），逐条达成才算真正到"Codex 级"：

| # | 能力 | 说明 | 判定标准（可验证） |
|---|------|------|------------------|
| G1 | FS 权限 | 能读/写工作区文件 | 能读 index.html 源码 |
| G2 | Shell 权限 | 能跑命令、看报错、操作 git | 能跑 `node --check`、能 commit |
| G3 | 自诊断循环 | 读日志 → 定位 → 假设 → 验证 | 能自己定位"重复日程"类 bug 的根因 |
| G4 | 自修改循环 | 改代码 → 验证 → 回滚 | 能修复上述 bug 并通过回归测试 |
| G5 | 外部资源 | MCP / ToolPkg / HTTP 动态加载 | 能现场装一个技能包并立即使用 |
| G6 | 记忆主权 | 记忆独立于宿主与会话，可导入导出 | 记忆导出 → 换宿主 → 导入后仍认得俪宁 |
| G7 | 产物持久 | 产物落盘为文件，可被引用 | artifact 是磁盘上的文件，不是聊天文本 |

**当前完成度**：

```
G1 ✗    G2 ✗    G3 ✗    G4 ✗
G5 △（接口预留：ToolPkg/MCP Bridge，未落地）
G6 △（C4 记忆设计完成，未实现）
G7 △（C1 产物设计完成，未实现）
```

一句话：**引擎与能力支柱的设计已经成形，被卡死的只有宿主权限（G1/G2/G4 依赖它）。**

## 三、差距分析：缺的到底是什么

| 维度 | 现在（PWA） | 目标（Codex 级） | 差距根因 | 靠什么补 |
|------|------------|-----------------|---------|---------|
| 宿主权限 | localStorage + DOM | FS + Shell | **浏览器安全模型** | 宿主外移（§四） |
| 循环引擎 | AgentLoop（成形） | 自主循环 + 可配轮次 + abort | 无实质差距 | 抽离成独立包复用 |
| 自诊断/自修改 | 无 | G3 + G4 闭环 | 碰不到源码 + 无 shell | G1/G2 达成后自然解锁 |
| 工具加载 | 内置 13 工具 | ToolPkg/MCP 动态加载 | 部分（接口预留） | C3 支柱落地（大脑层） |
| 记忆 | 无（设计完成） | 独立 Memory + 自动注入 | 未实现 | C4 支柱落地（大脑层） |
| 流式/并行 | 无 | stream + 工具并行 | 未实现 | P5 预留（大脑层） |
| 存储 | localStorage | 文件 / 云 | 边界 | StorageAdapter 抽离 |

**核心洞察**：大脑层能力（C1–C4 四支柱、AgentLoop、LLMAdapter）**不依赖宿主**——可以在任何地方实现。真正被浏览器卡住、必须靠宿主外移才能解锁的，只有 **G1 / G2 / G4**（FS、Shell、自修改）。其余差距都是"大脑层落地进度"问题，不是"宿主能力"问题。

**推论**：宿主外移是解锁 G1/G2/G4 的必要条件，但大脑层实现（C4 记忆、C1 产物）可以先行——即使宿主还没外移，也可以先在能跑的地方实现。

## 四、宿主外移路线（三段式）

### 原则

1. **大脑一次抽离，多宿主复用**：AgentLoop + LLMAdapter + ToolPipeline 抽成独立核心包，任何宿主 `register()` 就能跑。
2. **每个 Phase 都是可运行的**：做完就能用，不是半成品。
3. **先验证闭环，再上重框架**：先用最薄的壳验证"agent 能自己修 bug"这条闭环，证明假设后再决定是否引入 Cordis 级框架。

```
Phase A ──→ Phase B ──→ Phase C
冻结定稿     本地服务端宿主     桌面宿主 / 独立 Agent CLI
（现在）     （解锁 G1/G2）    （解锁 G4 完整闭环）
```

---

### Phase A — 冻结与定稿（现在，2026-08）

| 动作 | 内容 |
|------|------|
| 冻结 PWA 功能补丁 | 清单见 §五；仅重大数据损坏 bug 仍修 |

| 决策点 | 见 §六——大脑层在哪个载体实现、Phase B 用什么骨架 |

---

### Phase B — 本地服务端宿主（Node 进程）

**目标**：解锁 G1（FS）+ G2（Shell），验证 G3（自诊断）闭环。

**做法**（最小可行版，不引重框架）：

1. **核心包抽离**：把 index.html 里的 `AgentLoop` / `LLMAdapter` / `ToolPipeline` 逻辑抽成独立 Node 模块（PAA Core）。
2. **宿主 = Node CLI 进程**：初始工具集只要 3 个——
   - `fs.read(path)` / `fs.write(path, content)`（G1）
   - `shell.run(cmd)`（G2，白名单 + 确认）
   - 现有生活技能包（挂载复用）
3. **工作台 PWA 降级为远程 UI**：通过 HTTP/WebSocket 桥接调用核心包（可选，CLI 先跑通即可）。
4. **里程碑验收**：

```
$ paa run "帮我查一下日程模块为什么重复展开错误"
→ agent 读 expandRecurring 源码 → 定位 weekly 步长 bug → 给出修复 diff → 确认后写入 → node --check 验证
```

走到这一步，G1/G2/G3 全绿——这就是"agent 自己修工作台"的第一次真实闭环。

**刻意不做**（Phase B 阶段）：Cordis IoC、事件溯源、OS 级沙箱、Compaction、并行工具。这些是 DSH 的复杂度，等闭环验证通过、确有需要再加。

---

### Phase C — 桌面宿主（Tauri）或独立 Agent CLI

**目标**：解锁 G4 完整闭环（改代码 → 验证 → git 回滚），成为真正的"Codex 级入口型 agent"。

**两条候选路径**（不互斥，可先后）：

| 路径 | 说明 | 参考 |
|------|------|------|
| Tauri 桌面宿主 | FS + Shell 插件，离线优先，三端数据一致 | `TAURI_ROADMAP.md` 已规划 |
| 独立 Agent CLI | 终端形态入口（Codex 形态），工作台只是它的一个 skill | DSH CLI 思路 |

**关键迁移决策**（大脑层一次抽离后，各宿主只做适配）：

| 组件 | 去向 |
|------|------|
| 大脑层（AgentLoop/LLMAdapter/ToolPipeline） | PAA Core 独立包，多宿主复用 |
| 生活技能（13 tools） | 转成 ToolPkg 技能包，宿主无关 |
| 记忆（C4） | 文件存储，任何宿主可导入导出 |
| PWA UI | 降级为宿主之一 / 远程控制台 |

## 七、待俪宁确认

| # | 决策点 | 选项 A | 选项 B | 我的建议 |
|---|--------|--------|--------|---------|
| 1 | 大脑层能力（C4 记忆等）在哪实现 | 先在 PWA 里落地（快，但又要动前端，与冻结冲突） | 等 Phase B 核心包抽离后一起做（一步到位，前端保持冻结） | **B**。既然冻结已拍板，PWA 内做 C4 等于重新打开冻结面；核心包抽离时记忆系统作为第一个模块落地更干净 |
| 2 | Phase B 骨架 | 复用 DSH（TypeScript + Cordis，重框架） | 复用 Operit（Kotlin/Android，宿主不匹配） | **都不直接用**。PAA 抽自己的 Core 包：AgentLoop/LLMAdapter/ToolPipeline 三件套 + 3 个 FS/Shell 工具起步。DSH/Operit 只当参考，不当骨架 |
| 3 | Phase B 启动时机 | 现在开始（把 PAA Core 抽出来） | 等学业/RA 告一段落 | 取决于俪宁的时间优先级（P0 学业 > P1 RA 套磁 > P2 工具链 > P3 Numerai > P4 个人项目）。文档先落盘，代码随时可启动 |
| 4 | G3 自诊断的验证靶子 | 用工作台真实历史 bug（如 expandRecurring） | 造一个沙箱样例 bug | **用真实 bug**：更有说服力，且修复结果直接可用 |

## 八、一句话总结

> 前端 agent 是产品验证的临时壳，PAA 大脑是主线，宿主外移是解锁"agent 自己修自己"的唯一路径。该收手的是往壳里打补丁，该开始的是把大脑搬进有 FS/shell 权限的新壳。
